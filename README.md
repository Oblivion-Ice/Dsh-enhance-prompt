# dsh-enhance-prompt

DSH desktop plugin that adds an **enhance** control to `conversation.input.right`
and rewrites the current composer draft with one auxiliary model call.

> **Stable: `1.0.0`.** The control is a 16 px icon button with a session-isolated
> state machine, verified draft write-back (plain and reference drafts), real
> cancellation, and zh/en tooltips. `lib/` is generated by `build.mjs`; do not
> edit it. The release artifact is the packed tarball (see [Install](#install)).

## What is implemented

- **Host** (`src/host/*.ts`, built to `lib/host/*.js`)
  - route resolution: configured `provider`+`model` → Client-reported `model`
    searched through `ctx.llm.listProviders()/listModels()` → `no_route`;
  - one auxiliary request: `ctx.llm.prepareCall()` + `BlockAssembler`, one user
    message, `system` prompt, `dsh-timeout` deadline, no tools, no Session writes;
  - output cleanup (quotes, fences, whitespace) and `max-tokens` / over-length
    acceptance without truncation;
  - desensitized JSONL log at `$DSH_HOME/enhance/requests.jsonl` (sha256 + lengths,
    2 MB × 3 rotation, `logRequests: false` disables it);
  - Config schema (Schemastery) and field-level validation. Three fields are
    `.volatile()`, which is what makes them visible to the Client through the
    settings document (see [Settings](#settings)).
- **Client** (`src/client/*.tsx`, built to `lib/client.js`)
  - hand-written Typert contribution with a **real zod codec** (M0 review) for
    `enhance/run` — one method, one descriptor;
  - one `conversation.input.right` list entry, id `enhance`, order `10`;
  - state machine (`idle / enhancing / applied` + `error`) keyed by `sessionId`;
    stale responses are discarded by `seq` + `controller` identity;
  - **verified** write-back: every write is read back on the next frames and
    rolled back with `apply_failed` when the composer did not take it;
  - reference chips are preserved: only the text runs between them are
    rewritten (`referencesMode: 'replace-text'`), or the control is disabled
    (`referencesMode: 'disabled'`);
  - cancellation through `ns.run(input, signal)` — the Gateway injects the signal
    into the Host method and the Host request log records `aborted`;
  - i18n through `ctx.locale.register('enhance', { zh, en })`; the entry declares
    its locale so zh ↔ en switches the tooltip without a reload.
- `lib/` is entirely generated by `build.mjs` and ignored by version control.
  The module-loader envelope contract is documented in `docs/client-envelope.md`
  in the repository (deliberately not shipped in the tarball).

## Install

**Distribution decision: the packed tarball is the release artifact** (with the
repository junction kept only for development). No GitHub or npm publishing is
part of this release; `lib/` stays out of version control and is built by
`prepare`/`build`.

The desktop profile is managed by the Electron application, so its package is
installed with the bundled pnpm (the `dsh plugin --profile desktop` command is
reserved for the application):

```powershell
$profile = "$env:USERPROFILE\.dsh\profiles\desktop"
$pnpm    = 'D:\Deepseek\resources\runtime\primary-runtime\dependencies\pnpm\bin\pnpm.cjs'
cd $profile
node $pnpm add --offline D:\path\to\dsh-enhance-prompt-1.0.0.tgz
```

Then make it a profile layer and configure it. Add `dsh-enhance-prompt` to
`dsh.profile.bundles` in the profile's `package.json` (the package's own
`dsh.bundle.patch` then inserts the entry), and put **only the config row** in
the profile's `cordis.patch.yml`:

```yaml
# ~/.dsh/profiles/desktop/cordis.patch.yml
- id: enhance
  config:
    provider: deepseek-account
    model: deepseek-flash
    timeoutMs: 20000
```

For development, link the repository instead of packing:

```powershell
New-Item -ItemType Junction `
  -Path "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\dsh-enhance-prompt" `
  -Target "D:\Develop\dsh-enhance-prompt"
```

and use the full row in the profile patch (the bundle patch does not apply to a
plain dependency):

```yaml
- insert:
    - id: enhance
      name: "dsh-enhance-prompt"
- id: enhance
  config:
    provider: deepseek-account
    model: deepseek-flash
    timeoutMs: 20000
```

Do not apply both forms at once. Restart the application after installing the
tarball form (the renderer loads the bundle at boot); the junction form also
requires a page reload for a rebuilt Client.

Uninstalling: remove the bundle row and the patch row, then
`node $pnpm remove dsh-enhance-prompt` (or delete the junction). The Host boots
normally with no plugin row and no `enhance` namespace. The request log
directory `$DSH_HOME/enhance/` is data, not configuration, and is left behind;
delete it manually.

## Configuration

Profile entry (namespace = entry id `enhance`):

| field | default | volatile | notes |
|---|---|---|---|
| `enabled` | `true` | yes | `false` registers no slot entry |
| `minTextLength` | `1` | yes | `draft.trim().length` below this renders nothing |
| `referencesMode` | `replace-text` | yes | `replace-text` keeps chips; `disabled` disables the control on a chip draft |
| `maxInputChars` | `4000` | no | Host rejects larger input with `too_long` |
| `maxOutputChars` | `800` | no | target carried in the prompt; longer output is accepted whole and the log records `truncated: true` |
| `timeoutMs` | `20000` | no | end-to-end deadline (`timeout`) |
| `provider`, `model` | unset | no | both or neither; invalid provider becomes `no_route` |
| `logRequests` | `true` | no | write the desensitized request log |
| `shortcut` | unset | no | reserved; not implemented |

Route priority is strict: configured pair → Client-reported model → `no_route`.
Provider names are read from `ctx.llm.listProviders()`; none are hardcoded.

**Volatile fields are live.** `enabled`, `minTextLength`, and `referencesMode`
are `.volatile()`: a Host-side edit of those fields is committed into the running
plugin without a restart, and the new value is served at the next page load. The
Client reads them **once per activation**, so the control re-gates on a reload,
not on the edit itself.

**An invalid config removes the control.** A value outside its bound or of the
wrong type deactivates the plugin: the Host prints a field-level
`ValidationError` (`$.timeoutMs expected number but got abc`), the entry does not
activate, the `enhance` settings namespace disappears, and the Client registers
no control (this is the M4 §1.2 fix; M3 used to render a button that could only
answer `error: llm_failed`). Nothing else in the profile is affected.

## Behaviour

| phase | control | tooltip | click |
|---|---|---|---|
| `idle` | enabled, sparkle icon | 增强提示词 / Enhance prompt | starts one request |
| `enhancing` | enabled, spinning icon | 增强中... / Enhancing... | cancels that request |
| `applied` | enabled, revert icon | 恢复原文 / Revert to original (plus the undo hint below when relevant) | restores the click-moment draft exactly |
| `error` | enabled, sparkle icon | `error: <code>` | starts a new request |

- **Position**: `conversation.input.right`, id `enhance`, order `10` — in the
  composer tool row immediately left of the model selector, before Send.
- **Availability while a turn is running**: yes; enhancing only edits the draft.
  The control is disabled when the session is removed, while the input machine is
  `adjudicating`/`submitting`, or while a composer block is published.
- **Rendering rules**: a blank draft (below `minTextLength`) is **not rendered**
  (not greyed); with `referencesMode: 'disabled'` a chip draft is rendered
  disabled; a locked composer is rendered disabled. While `enhancing`, the control
  stays visible even if the draft becomes empty, so the cancel affordance does not
  disappear.
- **Extra safety**: if the draft is edited while a request is in flight, the
  response is discarded instead of overwriting the edit.

## Reference chips and the "revert restores exactly" promise

The composer publishes two projections of the draft:

- `draft` — flat clipboard text (a chip appears as its literal `@README.md` token);
- `occurrences[]` — structured reference chips (`source`, `ref`, `offset`, `length`,
  `label`, `clipboardText`, `appearance`), offsets in clipboard coordinates.

### `referencesMode: 'replace-text'` (default)

A chip is an **anchor**: no write ever touches it. The model receives the whole
draft (tokens included) and must return every token exactly once, in the same
order (the system prompt states this as a highest-priority rule). The answer is
split at those tokens into `chips.length + 1` text runs, and each run is written
over the editor's **detect** coordinates:

```text
detect = clipboard − Σ(chip.length − 1)      // a chip occupies one detect position
```

Runs are written last-to-first, so earlier spans stay valid, and the revision is
re-read before every call because `insertText(text, span)` refuses a span whose
`span.draftRev` is not the current revision.

Measured on a live composer (`.m3/exp-insert.out.txt`, five drafts, one chip at
the front, one at the end, two interleaved, an emoji draft, and a
multi-paragraph draft):

- every write was accepted, the resulting `draft` equalled
  `chip + run + chip + run…` exactly, and the chip count and refs were unchanged;
- the same drafts (plus a zh/en-mixed one and a multi-paragraph one) were then
  driven end to end through the real control (`.m3/exp-apply.out.txt`):
  `applied` for all six, chips intact, and the second click restored the original
  draft, chips included, in all six.

Any answer that does **not** carry the tokens exactly once and in order is
rejected: nothing is written, the draft is restored from the click-moment
snapshot, and the control reports `error: apply_failed`. Silent degradation is
not an option.

`referencesMode: 'disabled'` is the one-line fallback to M2 behaviour: a draft
with `occurrences.length > 0` renders a disabled control whose tooltip says
"请先移除引用再增强". No request is sent.

Attachments (images/files in `attachmentIds`) are not part of any text write and
are preserved in both modes.

### Why not a structured `setDraft`

`setDraft({ text, references })` exists and reconstructs chips, but it is only
useful for the *forward* write; a revert through it would rebuild chips rather
than restore them. The segmented path never touches a chip, so a failed write
cannot destroy one. The structured form is therefore not used at all.

## Write-back verification

`setDraft()` returns nothing and a blocked composer silently ignores the write.
Every write therefore goes through one helper (`applyDraft` in
`src/client/draft.ts`):

1. perform the write; an action that returns `false` or throws is a failure;
2. read the published `draft` **and** the chip `ref` sequence on the next frames
   (up to `APPLY_DEADLINE_MS`, 600 ms);
3. on any mismatch, restore the click-moment snapshot (same verified path) and
   report `apply_failed`; the button returns to a clickable `error` state.

The revert click uses the same helper. If the composer refuses *that* write, the
record stays `applied` (so the snapshot is not lost and the revert can be
retried); the draft is left exactly as it was.

This covers "the composer is blocked so the write was ignored": the write looks
successful at the API level and is caught by the read-back.

## Undo granularity (M4 §1.1)

The supported revert is the button; it restores the click-moment snapshot
exactly. Manual Ctrl+Z is **not** equivalent:

- a **plain** draft is written with one `insertText` over the whole draft, which
  is one independent undo entry — one Ctrl+Z restores the original in the live
  measurement (M4: `.m4/final-verify.out.txt`, the `### plain` block);
- a **reference** draft is written run by run (`chips.length + 1` runs, only the
  changed ones), and each `insertText` is its own undo entry. With 2 changed runs
  a single Ctrl+Z leaves a half-new draft; N presses are needed. The applied
  tooltip states this: `恢复原文（请用按钮回滚；手动撤销需按 2 次）` in the
  measured case.

Why not one transaction: the published `InputActions` face has no batch/merge
parameter and no `editor.update`-level action. `insertText` hard-codes the
`paste` history tag (one entry per call) and `setDraft` commits with
`history-merge` (it merges into the previous entry; measured in M4, a Ctrl+Z after
a plain `setDraft` enhancement also removed the user's typed draft). Merging N
runs would need a new Host API, so the plugin writes through the documented
actions, states the cost, and keeps the exact button revert. See
`docs/client-envelope.md` for the observed tag behaviour.

## Cancel semantics

Cancellation is **real**, not a local discard:

1. a click during `enhancing` aborts the client `AbortController`;
2. the call uses the Gateway's positional cancellation contract
   `ns.run(input, signal)` (`ns.run(input, { signal })` throws an arity error);
3. the Gateway injects `signal: AbortSignal` as the Host method's final parameter;
4. the Host's deadline/stream observe it and return `aborted`; the request log
   records `outcome: "error"`, `code: "aborted"`.

Measured in M2: the Host logged `aborted` 332 ms after the cancel click (limit in
C5.5: 500 ms). No error is shown and the draft is unchanged.

Editing or clearing the draft while a request is in flight is **not** a cancel:
the Host request runs to completion and the Client drops the result (M3 stress
items 3 and 4 record both cases, including the Host log lines).

## Settings

The Client half receives **no** loader config (`apply(ctx, config)` sees
`undefined`, measured in M2 experiment 0.2). Rendering settings therefore come
from the documented settings document:

```ts
ctx.remote.settings.describe()
// → { ok: true, value: { namespaces: [{ ns, value, revision, schema, … }] } }
```

- the namespace is the **profile entry id** — `enhance`;
- a namespace exists only when at least one of its Config fields is
  `.volatile()`, so `enabled`, `minTextLength`, and `referencesMode` are;
- `value` carries exactly those fields: `{ enabled, minTextLength, referencesMode }`;
- the read happens once, at Client activation, and is the only settings RPC the
  plugin makes. `describe()` answers every namespace the Host serves (21 other
  namespaces, ≈36 KB of JSON); there is no narrower read in the contract.

Two failure modes are deliberately different (M4 §1.2):

| observation | conclusion | effect |
|---|---|---|
| `describe()` **succeeds**, `enhance` namespace **absent** | the Host entry is not active (usually an invalid config) | no slot entry is registered; the Host stderr already carries the field-level `ValidationError`; a `console.warn` names the cause |
| `describe()` **fails** (no settings controller, refused call, malformed envelope) | the plugin cannot tell why | fall back to `enabled: true`, `minTextLength: 1`, `referencesMode: 'replace-text'` and render; a visible control beats a silently missing one |

An absent namespace is re-read for up to 800 ms (`SETTINGS_INACTIVE_GRACE_MS`)
before concluding "inactive", so a cold-boot activation race cannot hide the
control permanently. Activation waits at most 1.5 s (`SETTINGS_WAIT_MS`) for
`remote.settings` itself.

Because the read is once-per-activation, changing `enabled` / `minTextLength` /
`referencesMode` re-gates the control only after a **page reload**. With
`.volatile()` fields a Host-side edit is committed into the running plugin
without a restart, so the new value is already served at the next page load.

## Accessibility and state semantics

- A control that cannot act is **really `disabled`** — removed from the tab order,
  impossible to activate into a no-op — rather than `aria-disabled` while still
  focusable. `aria-disabled` is not set anywhere.
- A disabled button shows no native tooltip, so the explanation is carried by the
  wrapping `<span title="…">`: hovering the control still shows the reason, and
  `aria-label` mirrors it for screen readers. Enabled states carry both.
- `error` behaves exactly like `idle` (clickable, starts a new request) and keeps
  `data-enhance-phase="error"` so the failed state remains observable. This is
  deliberate.
- The icon is `aria-hidden`; the button has `aria-label` (phase-specific) and
  `aria-busy` while enhancing.

## Model-visible ⟺ logged deviation

The enhanced prompt is a pre-send draft. It is not written to the Session and
never enters conversation history, so the Host cannot reconstruct this exact
request from the Session log. This is an intentional deviation from the
`model-visible ⟺ logged` invariant: the input does **not** participate in the
conversation context or KV cache. The plugin's own log records only a SHA-256
hash and lengths, never the original text or the output.

## Build / test / typecheck

`build.mjs` produces the whole of `lib/` in one pass (esbuild):

```powershell
npm run verify        # build + node --test + tsc gate
# or individually:
node build.mjs
node --test "test/*.test.ts"
node node_modules\typescript\bin\tsc -p tsconfig.build.json
```

- Host TypeScript is compiled per file to ESM under `lib/host/` and
  `lib/shared/`; `lib/index.js` is generated.
- `src/client/index.tsx` is bundled to `lib/client.js` inside the
  `window.__ModuleLoader__.load({ id, factory })` envelope. `react` stays
  external; `zod` and both locale dictionaries are inlined (~35 KB bundle;
  contract in `docs/client-envelope.md`).
- `tsc` runs with `noCheck: false` and `skipLibCheck: true`; `src/types/` carries
  minimal ambient declarations for the Node builtins and DSH packages the sources
  actually use, and the client context has a local structural `ClientContext` (it
  is the loader seat, not an imported package). The gate is **zero errors with no
  `@ts-expect-error`**. A use beyond the shims fails the gate — that is
  intentional, and widening a shim is a review decision.
- `rm -rf lib && node build.mjs` reconstructs everything; two consecutive builds
  are byte-identical.

Tests cover route priority, every error code, cleanup, abort, log redaction,
rotation, configuration bounds, volatile-cell reading, the runtime guards, the
generated bundle (envelope laziness, single external, shared-protocol marker,
real zod codecs, no leftover experiment probes, settings-driven gating, the
inactive-namespace gate), the state machine (including the stored undo count),
the clipboard→detect mapping, `applyDraft` verification, the settings reader and
its fallbacks, and the zh/en key-set equality.

## Known limitations

- **Manual undo is not the revert path.** A reference draft needs one Ctrl+Z per
  changed run and passes through a half-new draft; a plain draft is one entry.
  Use the button; the tooltip states the count when it exceeds one. Merging the
  runs needs a Host API that does not exist (see Undo granularity).
- **Settings are read once per Client activation**, so a change to `enabled` /
  `minTextLength` / `referencesMode` needs a page reload to re-gate the control.
- **An invalid config hides the control by design** (§1.2). The user-visible
  explanation is the Host's stderr `ValidationError`; the Client only logs a
  `console.warn`. A control that always fails with `llm_failed` was judged worse.
- **Reference detection depends on the composer's `occurrences` table.** If a
  future host publishes chips without matching `offset`/`clipboardText`, the
  mapping is rejected (`references_unsupported`) rather than guessed; the control
  stays usable for plain drafts.
- **The model must preserve the `@` tokens.** An answer that renames, drops, or
  reorders a token is rejected with `apply_failed` and the draft is restored; it
  is not written partially.
- **`composerBlock` is not a standard slot prop.** The control reads the
  Conversation service's per-session composer-block registry (feature-detected,
  read-only) to honour "composerBlock → disabled". If that internal field is
  absent in a future host, the control simply ignores that one lock signal.
- **`minTextLength` is a client-side render rule**, while `maxInputChars` remains
  a Host rule (`too_long`).
- `input.draft` is `projection.clipboardText`, not the editor's live text; the
  plugin reads it through the published state and writes through the published
  actions, so it inherits the host's projection semantics.
- **The tarball install is application-managed.** `dsh plugin --profile desktop`
  refuses by design; use the bundled pnpm path in [Install](#install), or the
  application's plugin UI.
- **The undo hint's count is changed runs, not chips.** A run that the model
  left byte-identical is not written and not counted.

## i18n

`locale/zh.json` and `locale/en.json` carry the same key set (`title`,
`enhancing`, `revert`, `undoHint`, `references`, `locked`, `error`). The Client
registers them with

```ts
ctx.effect(() => ctx.locale.register('enhance', { zh, en }), 'enhance: dictionaries')
```

and declares `locale: 'enhance'` on the slot entry, so the framework supplies a
locale-aware `t` seat and re-renders the entry on a language switch. Tooltips,
`aria-label`, and the error template all follow the active locale; tests fail if
the two key sets diverge.
